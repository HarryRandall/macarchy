Why it looks like this

System Settings, deliberately

Sidebar plus grouped Form rows is the idiom this app replaces, so borrowing it means nothing new to learn. Sections are grouped by what you're changing — Appearance, Behaviour, System — not by which daemon owns it. You think "make the gaps bigger," not "reconfigure yabai."

The live preview

Borrowed from yabUI, which puts a proportional window map front and centre. Gap and padding are spatial values, so a number alone is a poor control — the miniature makes the slider legible before it touches the real desktop.

ref · github.com/4hmedk/yabUI

The console strip

Also from yabUI, whose Activity tab logs every command with its success or failure. When an app is a face over four CLIs, hiding the shell-out is the wrong instinct — showing it is what makes the thing debuggable and trustworthy.

Every control writes one line here. If a daemon rejects a value, its stderr lands in the row and nothing is persisted.

No Save button

Changes apply live and debounce at 80 ms; the commit writes settings.env and snapshots. Saving is a concept from a world where the app owns a document — here the daemon is already the source of truth.

Read-only means owned elsewhere

The Borders pane shows colour greyed with a pointer back to Themes. That's the bordersrc ownership split made visible: theme owns colour, settings owns geometry. A rule you can see in the UI is a rule you won't accidentally break in a dotfile.

Surfacing the temporary

The macOS 27 Space-switching workaround currently lives in a comment at skhdrc:55. Advanced lists it with the date it was added, so a stopgap can't quietly become permanent.
